# 词环项目复盘与后续事项

> 记录日期：2026-08-01
> 对应路线：[性能、数据升级与异常恢复路线图](./performance-roadmap-gap-analysis.md)

## 一、当前结论

路线图主体及后续生产增强已经完成并验证：生产构建、当前 92 项单元与结构测试、27 项 Playwright、正式性能基线、数据来源复现、Windows 生产冒烟和私有发布均已闭环。

当前没有阻塞发布的遗留功能。后续事项属于工程固化、生产环境测量和长期体验优化。

## 二、项目感悟

### 1. 性能优化必须由真实链路数据驱动

文件变小不等于用户操作一定变快。Range 根索引从约 338KB 拆为字母索引后，额外串行请求的固定延迟抵消了部分收益；将 5KB 根映射内嵌后，原生 206 Range P50 才从 14.9ms 降到 10.9ms。

以后做性能判断时，应同时查看：

- 绝对耗时，而不只看阶段占比；
- 首次与重复操作；
- 206、200、损坏和断网等独立场景；
- 请求数量、传输大小和解析耗时。

### 2. 本地应用同样存在分布式一致性问题

多标签页并发写入、旧 revision 覆盖、批量性能样本合并、清空后的旧数据复活，本质上都是一致性问题。浏览器本地存储不能只按单页面状态设计，需要 revision、稳定 ID、锁、合并规则和 tombstone。

### 3. 降级链路是产品能力，不只是异常分支

IndexedDB 禁用、数据库损坏、localStorage 配额耗尽、Range 网络中断、自动播放受阻都可能真实发生。降级逻辑必须做到：

- 不覆盖尚可恢复的原数据；
- 明确告诉用户当前状态；
- 保留恢复入口；
- 有浏览器级测试，而不只依赖单元测试。

### 4. 测试失败需要区分产品问题与测试基础设施问题

首次 Playwright 的 3 项失败来自测试助手在模拟 IndexedDB 失效后仍强制读取 IndexedDB，而不是产品降级失败。排查时应先确认失败发生在产品断言、测试准备还是测试清理阶段。

### 5. 聚合指标可能隐藏真实结论

200 整分片回退、片段损坏和网络中断混入总体中位数后，会改变 Range 占比的含义。性能报告必须保留原始 trace，并按场景、首次/重复和资源缓存状态分组，避免用一个总体数字替代判断。

### 6. 可复现构建需要证据链，而不只是来源名称

“使用 ECDICT、Whisper 和 FFmpeg”不足以复现结果。完整证据至少包括：

- 上游 commit 和源文件 SHA-256；
- 模型 snapshot commit、权重文件 SHA-256；
- 工具版本及二进制 SHA-256；
- 生成报告与最终运行时资产哈希；
- 能证明源文件确实生成当前产物的重建比对。

### 7. 数据版本、代码版本与测试报告必须绑定

即使只补充词典 metadata，也会改变数据内容版本。浏览器验证和性能基线必须记录应用构建号与数据版本，否则历史报告可能被错误地用于当前产物。

## 四、执行原则

- 先测量，再改变结构。
- 同时保留绝对值、比例和分场景数据。
- 降级时优先保护原始数据和可恢复性。
- 自动测试覆盖机制，真人复核覆盖体验。
- provenance 只记录能够验证的事实，不使用推测值。
- 新报告必须绑定应用构建号和数据版本。

## 五、建议的下一步

P0 与 P1 工程项已完成。下一性能里程碑是用 30–50 轮慢速网络同条件专项基线确认下一词预载收益；P2 可同时按 [人工体验与长期数据验收单](./manual-experience-validation.md) 积累真人证据，不阻塞当前版本。

## 七、第二轮性能与发布增强（2026-08-01）

### 实施结果

- 新增 Windows 生产冒烟 CI 和可本地复用的 `npm run smoke:production`，固定端口 3000，记录唯一日志与 PID，仅关闭本轮服务。
- 生产冒烟覆盖首页客户端激活、所有客户端 JavaScript、红宝书 6550 词、音频运行时索引及词典 `206`/`Content-Range`/响应长度。
- 新增空闲词典索引预取：当前词优先，其余页面内容按较长单词优先，最多 3 个字母、2 个并发、192KB 预算。
- 省流量、2G、离线和后台标签页自动跳过预取，原有 200 回退、损坏片段、断网和内容版本校验保持不变。
- 跨版本性能比较增加兼容性门槛；四种网络条件使用各自历史文件，无兼容报告时输出“无可比基线”且不产生告警。
- 性能诊断 schema 升至 3，构建产物注入运行模式；生产小样本的页面模式与运行器模式均为 `production`。
- Sites 私有版本 1 发布成功：<https://wordloop-kaoyan-2027.ynvdb2s6s2.chatgpt.site>。

### 复核结果

- 最新构建：`0.1.0+1520c7e76ef4.2d06aeb2880e`；数据版本仍为 `a9b0000495913c32`。
- `npm run lint`、`npm run typecheck`、生产构建和 87/87 单元与结构测试通过。
- Windows 本地生产冒烟通过，结束后端口 3000 空闲且无残留 PID。
- 250ms 高延迟 5 轮方向性样本中，首次查词 P50 为 `81.7ms`、P95 为 `286.7ms`；相对旧 P50 `343.7ms` 约降低 76%。样本量不足以替代正式 30–50 轮里程碑基线。

### 新增经验

- 后台预取必须同时有触发时机、网络策略、并发限制和字节预算；只写一个 `prefetch` 调用无法形成可控能力。
- 基线兼容性应在比较入口统一判定，而不是依赖报告使用者记住网络和设备差异。
- Windows 冒烟必须验证真实客户端入口；vinext 使用内联模块脚本与 `modulepreload`，不能只查找传统 `<script src>`。
- 音频预载不能直接复用单元素方案并连续改写 `src`，否则可能牺牲当前词播放来换取下一词命中。

## 八、有界下一词音频预载（2026-08-01）

### 实施结果

- 播放器固定保留两个浏览器原生音频元素：主元素负责当前词，第二个元素只预载下一词。
- 学习队列推进时，命中的下一词元素直接提升为主播放元素；释放旧主元素后才为新的下一词创建预载，不会突破 2 个有效媒体源。
- 预载只在页面空闲、在线、前台且非省流量/2G 条件下执行，并监听网络与页面可见性变化。
- 不新增 Cache Storage 音频副本，继续复用浏览器对媒体片段、HTTP Range 和解码数据的原生缓存策略。
- 设置页显示音频预载池占用、固定上限和下一词加载状态；性能样本标记 `preloadTarget`、`poolEntries` 与 `poolLimit`。

### 复核结果

- `npm run lint`、`npm run typecheck`、生产构建和 88/88 单元与结构测试通过。
- `npm run test:e2e:production` 的 26/26 项通过；新增浏览器用例验证初始学习与评分切词后均只有两个有效音频源。
- 本轮完成机制、容量和回归验证；慢速网络下下一词首播 P50 是否降低至少 25%，留待 30–50 轮专项基线判定。
