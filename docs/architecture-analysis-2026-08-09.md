> 审查日期：2026-08-09  
> 审查方式：只读静态审查  
> 项目：WordLoop

## 1. 当前架构概览

### 1.1 审查范围与基线

本次对运行时代码、API 路由、业务库、持久化逻辑、构建与数据脚本、单元测试和 E2E 测试进行了只读静态审查。

- 运行时代码约 58 个 TypeScript、TSX 和 CSS 文件。
- 源码、脚本和测试合计约 105 个代码文件。
- 全局样式文件约 5305 行。
- 未逐条展开 `public/data` 中的大型生成数据，只检查其生成、版本、完整性和加载链路。
- 没有修改、删除、移动业务文件。
- 为避免生成 `dist`、测试结果和运行日志，本轮没有执行构建或测试，因此不对当前测试是否通过作确认。
- 审查时分支为 `codex/follow-up-hardening`，相对远端 ahead 41。
- 审查期间工作区存在其他并行进程产生的未提交修改，本报告采用审查结束时观察到的工作树快照。

### 1.3 当前架构模式

当前项目属于：

- 本地优先的模块化单体。
- React/Next.js 客户端重应用。
- “纯函数核心 + 命令式外壳”模式。
- 以 `reviews` 事件记录为依据、以 `wordProgress` 为物化投影的轻量事件溯源设计。

它不是严格的 Event Sourcing，因为事件记录和派生状态都被持久化，且部分业务状态无法完全由事件重建；项目也没有形成明确的应用服务、仓储接口和依赖倒置层。

### 1.4 核心业务流程和数据流

#### 启动与恢复

1. `page.tsx` 加载红宝书数据和审计元数据。
2. `useStudyPersistence` 同时检查 IndexedDB、localStorage 回退状态和恢复副本。
3. `study.ts` 对历史存储格式执行规范化和迁移。
4. 恢复后的数据被拆成三十余个 React 状态。
5. 页面根据这些状态重新计算今日队列、薄弱画像、洞察和展示模型。

#### 学习评分

1. 用户提交评分。
2. `page.tsx` 调用 FSRS `applyRating`。
3. 同时更新进度、复习事件、错词、撤销栈、会话位置和提示。
4. 页面重新汇总完整 `StoredState`。
5. `useStudyPersistence` 防抖保存。
6. `storage.ts` 在同一事务中写入全部状态域。

#### 测验流程

测验题生成位于 `lib/quiz.ts`，测验会话局部状态位于 `QuizView`，排程、错词和复习记录更新又回到 `page.tsx`。一个业务用例横跨三层，事务边界不清晰。

页面注释提到“每日首次或到期词首次”，但实际判断只检查当天是否已经作答。到期词是否应在同一天再次改变排程，其业务含义目前“不确定”。

#### 查词与 AI

1. `useSelectionLookup` 读取 DOM 选区和弹层坐标。
2. 依次查询词书、缓存、词典分片、完整词典和 AI 接口。
3. 更新查词历史、查词统计、音标和薄弱信号输入。
4. AI 补全和教练通过多个 API 路由访问 OpenAI-compatible 服务。

该流程同时包含浏览器交互、数据访问、缓存、业务统计和远程接口编排。

#### 洞察与薄弱信号

`weak-signals.ts` 汇总查词、猜错、测验、FSRS、回忆耗时和顽固词数据，随后被 `insights.ts`、`session-summary.ts`、`HistoryView`、`WordCard` 等重复消费。

当前主要调用关系：

- 页面和组件 → hooks、`learning`、`weak-signals`、`insights`
- `study` → `learning`、`quiz`
- `quiz` → `learning`、`study` 类型
- `session-summary` → `weak-signals`
- 持久化 hook → `storage`、`backup`、`recovery`
- API 路由 → `api-guard` → 外部 AI Provider
- 数据脚本 → `public/data` 和 generated TypeScript 文件

## 2. 当前架构优点

### 2.1 核心算法具有较好的纯函数基础

FSRS 排程、队列、题目生成、词义规范化、句子索引和多数薄弱信号计算都以纯函数实现。这为后续划分领域层提供了良好基础。

### 2.2 本地数据保护设计较完整

项目已经考虑：

- IndexedDB 主存储。
- localStorage 回退。
- 自动备份。
- 恢复副本。
- 多标签页 revision/CAS 冲突。
- 写入排队。
- 导入前保护。
- 历史数据迁移。

这说明项目重视真实用户学习数据，而不是把本地持久化当作简单缓存。

### 2.3 事件与投影具有恢复能力

`reviews` 保留了复习事实，`wordProgress` 可以由历史事件重建。即使物化进度损坏，仍有一定恢复空间。这是当前架构中最值得保留的设计。

### 2.4 静态数据供应链较成熟

词书、词典、音频具备提取和规范化脚本、分片和索引、内容版本、Hash 校验、来源报告和数据完整性测试。

### 2.5 测试覆盖业务规则较广

薄弱信号、学习调度、测验、洞察、会话总结、数据生命周期、并发和 E2E 都有覆盖。`signal-flow.spec.mjs` 对跨模块联动尤其有价值。

### 2.6 部署适配层较薄

Worker 与构建插件主要承担框架适配，没有反向侵入大量业务逻辑。当前没有拆分微服务的必要。

## 3. 当前存在的问题

### 3.1 职责划分问题

#### God Component：`app/page.tsx`

该文件同时负责：

- 三十余个状态。
- 数据加载和兼容迁移。
- 页面路由。
- 学习评分。
- 测验结果。
- 撤销。
- 会话启动和结束。
- 洞察投影。
- 持久化快照组装。
- 快捷键。
- Toast、音频和焦点控制。
- 大型子组件装配。

文件规模只是表象，真正问题是应用服务、领域事务、UI 状态和 composition root 全部集中在同一组件。

影响：

- 修改评分规则时可能同时影响撤销、持久化、会话和 UI。
- 很难对“完成一次评分”作为原子业务操作进行测试。
- 新增功能通常需要继续向 `page.tsx` 增加状态、memo 和回调。

#### God Hook：`useStudyPersistence`

该 hook 同时承担存储读取、localStorage 回退、CAS 并发、多标签页同步、恢复决策、自动备份、导入导出、重试、清空学习记录、UI 状态和通知。

它实际上是一个持久化状态机，但使用大量 ref、布尔值和 effect 隐式表达状态，没有显式状态转换表。其中“清空学习记录”属于业务用例，不应由基础设施 hook 负责。

#### God Module：`weak-signals.ts`

该模块同时包含：

- 薄弱信号检测。
- 阈值策略。
- 聚合画像。
- 稳定性判断。
- 配对回忆。
- 冲刺候选。
- 治疗动作选择。
- 历史趋势。
- 时间线。
- CSV 导出。
- 中文展示文案。

它跨越领域规则、应用策略、查询投影和展示格式四种职责，是目前最明显的业务 God Module。

#### 大型视图组件

`HistoryView`、`WordCard`、`SettingsView` 和 `QuizView` 接收宽泛 props，并在视图内部继续执行统计或流程状态管理。

#### 全局样式单体

`globals.css` 约 5305 行，学习、词本、历史、设置、测验、查词和全部响应式规则都在一个文件中。任何功能的移除、拆分或命名调整都需要在全局文件中进行人工关联检查。

### 3.2 模块边界问题

#### 数据模型、存储模型和业务逻辑混合

`study.ts` 同时定义业务实体、UI 数据类型、完整 `StoredState`、存储版本、旧数据迁移、字段规范化和部分统计逻辑。

因此修改业务实体时，容易同时触发存储迁移、测试和 UI 类型变更。存储 DTO 与领域实体没有边界。

#### 领域依赖方向不稳定

`study.ts` 依赖 `quiz.ts` 的规范化函数，而 `quiz.ts` 又依赖 `study.ts` 的类型。这不一定构成运行时循环，但构成概念上的双向依赖。

更合理的方向应是：

- 领域模型不依赖持久化规范化。
- 测验领域不依赖全局存储模型。
- 存储映射层可以依赖领域类型。

#### UI 直接承担业务投影

`BooksView`、`WordbookView` 和 `HistoryView` 会直接遍历进度、复习记录和查词数据计算统计。相同业务口径可能在不同视图中逐渐分叉。

#### 字符串成为隐式模块协议

`session-summary.ts` 通过判断中文标签是否以“查过”“猜错”“拼写测验错”等字符串开头，对薄弱信号进行分类。

这意味着：

- 修改展示文案可能静默破坏统计。
- 类型系统无法检查遗漏。
- 国际化或新信号扩展困难。
- 领域标识和 UI 文案无法独立演进。

这是明确的高风险边界问题。

#### AI Provider 逻辑重复

多个 API 路由重复实现 Provider 环境变量读取、`/chat/completions` 请求、超时、Markdown JSON 清理、错误解析和内容校验。

新增 Provider、调整超时或统一日志时，需要修改多个路由。

#### 查询领域和 UI 几何混合

`SelectionLookupState` 包含查询结果，也包含坐标和弹层状态；`useSelectionLookup` 同时处理 DOM 选择、词典仓储、缓存、AI 回退和统计写入。这使查词能力无法脱离当前弹层复用。

### 3.3 可维护性问题

#### 一次业务操作由多次状态写入构成

评分和测验结果通过多次 `setState` 更新相关数据。虽然 React 通常会批处理，但业务一致性依赖 React 调度行为，而不是显式领域事务。

理想状态应是输入一个命令，得到一个完整的新业务状态和领域事件。

#### 完整快照写放大

虽然 IndexedDB 已按状态域保存，但每次仍构造并写入全部状态域。

随着复习历史、补全和测验记录增长：

- 任一小设置变化也会序列化大型数组。
- 保存成本随历史数据增长。
- 新增字段需要同时修改页面汇总、StoredState、拆分、合并和迁移。

#### 重复计算和长期性能风险

薄弱画像、趋势、冲刺候选、周报和历史图表会针对同一批数据反复扫描。复习事件持续累积，因此计算量会随使用时间增长。

在当前约 6549 个学习项规模下仍可能可接受，但长期应考虑按事件增量维护投影，而不是每次全量重算。

#### 时间口径分散

本地自然日、周起点、日期 key 和窗口范围在多个模块分别实现。学习软件对时区和跨午夜行为敏感，重复实现容易导致统计、排程和 E2E 口径不一致。

#### 模块级可变状态形成隐藏依赖

存储 revision、写入队列、性能诊断缓存和音频实例存在模块级单例状态。这些单例可能合理，但缺少明确生命周期，增加测试隔离和热重载复杂度。

#### 部分测试阻碍安全重构

`rendered-html.test.mjs` 直接读取源码并用正则检查函数名和字符串。这种测试验证的是实现形状而不是行为：

- 移动文件或重命名函数会导致无意义失败。
- 行为真正退化时也可能继续通过。
- 会人为阻碍模块拆分。

#### 业务指标语义仍有不确定项

以下规则应在重构前由产品口径确认：

- “冲刺当场达标”“冲刺后仍薄弱”“复发”是否代表同一时间窗口。
- 累计猜错是否永久保留，还是应存在恢复条件。
- 到期词当天已经参加测验后，是否允许再次修改 FSRS。
- API 限流是否只服务单用户部署。若未来多实例公开部署，当前进程内 bucket 不具备全局一致性。

这些内容目前均应标记为“不确定”，不能在架构重构中顺便改变。

## 4. 模块职责分析

### 4.1 页面编排模块

职责：

- 初始化全局学习状态。
- 装配所有功能模块。
- 响应用户操作。
- 在不同页面间切换。

存在的问题：

- 承担了领域服务、应用服务、状态仓库和 UI 控制器职责。
- 业务操作没有显式事务边界。
- 子组件 props 接口过宽。

建议：

- `page.tsx` 只保留应用装配、顶层导航和页面容器。
- 将评分、测验、撤销、开始会话等提取为应用用例。
- 将跨功能状态收敛到明确的 reducer/store。
- 子组件只接收面向展示的 view model 和少量命令。

### 4.2 学习领域模块

职责：

- FSRS 排程。
- 复习事件。
- 学习进度。
- 今日队列。
- 顽固词。
- 考试计划。

存在的问题：

- `learning.ts` 还包含展示格式和多个次级领域。
- `study.ts` 将领域类型、存储 DTO、迁移和统计混合。
- 存在概念双向依赖。

建议：

- 将复习、会话、计划、词书范围拆成学习领域内部子模块。
- 领域实体与 `StoredState` 分离。
- `formatInterval` 等展示逻辑移至 presentation formatter。
- 明确 `ReviewEvent` 是事实，`WordProgress` 是投影。

### 4.3 测验模块

职责：

- 测验模式。
- 题目生成。
- 答案判断。
- 活跃测验恢复。
- 测验结果对 FSRS 的影响。

存在的问题：

- 会话状态分散在页面、组件和 `lib/quiz.ts`。
- 排程策略与 UI 回调耦合。
- 页面注释和实际规则存在口径差异。

建议：

- 建立独立 `assessment` 模块。
- 用 `StartQuiz`、`SubmitAnswer`、`FinishQuiz` 等用例管理完整状态转换。
- “是否写入 FSRS”作为显式策略，并用业务测试固定口径。

### 4.4 薄弱信号与洞察模块

职责：

- 汇集不同来源的学习信号。
- 判断薄弱维度。
- 选择强化方式。
- 构建冲刺。
- 生成历史趋势和周报。

存在的问题：

- 聚合、决策、报表和文案全部放在一起。
- 中文字符串被用作结构化信号。
- 多个报表重复扫描相同历史。
- “治疗策略”与“分析报表”变化频率不同，却共享同一模块。

建议：

- 拆成 `signal-detection`、`weakness-policy`、`intervention`、`projections`。
- 信号使用稳定枚举或类型 ID，中文标签只在 UI 映射。
- 构建统一的只读学习画像投影供多个页面消费。

### 4.5 持久化模块

职责：

- IndexedDB 状态保存。
- 回退和恢复。
- 备份。
- 多标签页并发控制。
- 导入导出。

存在的问题：

- hook 实际承担复杂状态机，但状态不显式。
- 仓储实现直接认识完整 UI 状态。
- 业务操作混入基础设施。
- 每次写入全部状态域。

建议：

- 定义 `LearningRepository`、`SettingsRepository`、`BackupRepository` 等端口。
- 使用显式状态机表示 loading、ready、dirty、saving、conflict、recovering。
- 让存储 DTO 和迁移只存在于 infrastructure 层。
- 第一阶段保持现有 schema，不应在拆模块时同时迁移用户数据。

### 4.6 查词与 AI 模块

职责：

- 选区识别。
- 本地词书和词典查询。
- 远程 AI 回退。
- 词义补全。
- 查词统计。

存在的问题：

- UI 坐标、查询服务、缓存和统计写入混合。
- API Provider 客户端重复。
- 远程返回解析散落在各路由。

建议：

- 拆成纯 `DictionaryService`、查询仓储和 selection UI controller。
- 建立统一 `OpenAICompatibleClient` 基础设施适配器。
- 每个 API 路由只保留输入验证、用例调用和 HTTP 响应转换。
- Prompt 和返回结构校验归属于对应应用用例。

### 4.7 UI 组件和样式模块

职责：

- 展示学习、词本、测验、轨迹和设置。
- 处理用户交互和响应式布局。

存在的问题：

- 多个组件同时计算业务统计。
- 组件接口过宽。
- 全局 CSS 缺少功能边界。

建议：

- 每个 feature 提供自己的 view model selector。
- 将大型组件按稳定 UI 区块拆分，但不要把每个小元素都组件化。
- 样式按 feature colocate，保留少量全局 token、reset 和 layout。

### 4.8 数据脚本与部署模块

职责：

- 词书提取。
- 词典分片。
- 音频索引和修正。
- 数据来源验证。
- 构建信息生成。
- 生产环境验证。

存在的问题：

- 脚本数量较多，输入、输出和生成文件归属主要依靠命名约定。
- generated 文件会被构建流程覆盖。
- 数据 pipeline 与运行时代码的契约主要依赖测试维持。

建议：

- 按 `vocabulary`、`dictionary`、`audio`、`release` 分类。
- 为每条 pipeline 明确输入、生成物、schema 和验证命令。
- generated 文件只允许由统一入口生成，避免普通运行命令产生意外工作区变化。

## 5. 推荐的新架构设计

推荐保持模块化单体，不建议拆微服务。采用“按业务功能纵向切片 + 每个功能内部轻量 Clean Architecture”的结构。


### 模块通信规则

1. UI 只能调用 application use case 和 selector。
2. application 可以调用 domain 和 ports。
3. domain 不依赖 React、HTTP、IndexedDB、localStorage 或具体日期来源。
4. infrastructure 实现 ports，并在 `app/providers` 中注入。
5. 跨领域通信优先使用明确的命令和返回结果。
6. 只有确有多个消费者时才引入领域事件，不建议一开始建立复杂全局事件总线。
7. 业务状态改变应形成一次完整事务，而不是由组件分别修改多个数组。
8. 持久化层只认识存储 DTO，并通过 mapper 转换为领域状态。

### 为什么更合理

- 按业务功能查找代码，而不是在 `components/hooks/lib` 三个技术目录之间跳转。
- 业务规则与框架生命周期分离，可直接进行单元测试。
- 新增测验模式只影响 `assessment`，新增薄弱信号只影响 `weakness`。
- Provider、IndexedDB 或部署平台变化不会进入领域层。
- UI 文案变化不再影响统计规则。
- 可以逐模块迁移，不需要一次性重写。

## 6. 重构优先级

### P0（必须优化）

1. **显式化持久化状态机**

   这是用户数据安全边界。当前大量 ref 和布尔状态难以证明所有冲突、导入、恢复路径都安全。

2. **提取评分、测验、撤销的原子应用用例**

   核心业务操作当前由多次状态写入组成，增加局部更新和未来功能联动风险。

3. **分离领域模型与 StoredState/schema migration**

   当前每次领域模型变化都可能影响已有本地数据，扩展风险高。

4. **用结构化 ID 替换中文信号字符串协议**

   当前文案调整可能静默破坏冲刺维度统计，是明确的隐藏依赖。

5. **确认测验与冲刺业务口径**

   在业务规则“不确定”的情况下拆模块，容易把现有模糊语义固化到新架构。

### P1（建议优化）

1. 拆分 `weak-signals.ts` 的检测、策略、投影和展示职责。
2. 将 `page.tsx` 收敛为 composition root。
3. 拆分 `useSelectionLookup` 的 UI 控制器和查询服务。
4. 合并重复的 AI Provider 客户端。
5. 为 History、WordCard、Books 等组件建立 view model。
6. 统一日期、自然日和统计窗口逻辑。
7. 用行为测试替换源码正则测试。
8. 按 feature 拆分全局 CSS。

### P2（长期优化）

1. 将全量重算投影演进为增量或缓存投影。
2. 将全快照保存演进为按变更域写入。
3. 拆分性能诊断的存储、度量和报告职责。
4. 整理数据生成 pipeline 及 generated 文件边界。
5. 如果未来转为多用户、多实例部署，再升级持久化限流和服务端可观测性。
6. 评估历史事件归档策略，但不得破坏进度重建能力。

## 7. 渐进式重构方案

### 阶段1：固定业务契约，清理高风险隐式依赖

优化目标：

- 不改变存储 schema 和用户行为。
- 固定评分、测验、冲刺和薄弱判定口径。
- 消除字符串协议和重复时间逻辑。
- 为关键现状建立特征测试。

涉及模块：

- `weak-signals.ts`
- `session-summary.ts`
- `insights.ts`
- `quiz.ts`
- 日期工具
- 对应单元测试和 E2E

预期收益：

- 先建立可靠边界，降低后续移动代码时的语义漂移。
- 文案、报表和领域规则可以独立调整。
- 明确哪些行为是产品要求，哪些只是当前实现。

风险：

- 历史报表和冲刺指标可能因口径澄清发生变化。
- 必须保留兼容映射，避免旧记录无法解释。
- 开始前必须重新建立干净基线。

### 阶段2：提取应用用例，缩小页面和组件

优化目标：

- 将评分、撤销、测验、会话和查词写入变成原子命令。
- 将页面状态收敛为 reducer/store。
- 将业务投影从组件移出。
- 降低宽 props 和跨层回调数量。

涉及模块：

- `app/page.tsx`
- `QuizView`
- `WordCard`
- `HistoryView`
- `useSelectionLookup`
- `useAiCoach`
- learning、assessment、weakness application 层

预期收益：

- 核心操作可以脱离浏览器进行测试。
- 页面只负责装配和导航。
- 新增功能不再需要修改一个 2000 多行的中心组件。
- React 状态与领域事务边界一致。

风险：

- 撤销、会话推进、自动播放和 Toast 的执行顺序容易发生回归。
- reducer 初期可能只是把复杂性换了位置，必须按用例拆分，而不是创建新的 God Store。
- 此阶段仍应复用现有持久化格式。

### 阶段3：重构持久化边界并优化投影

优化目标：

- 建立仓储接口和显式持久化状态机。
- 将 schema migration 限制在 infrastructure 层。
- 支持按域增量保存。
- 为长期历史建立可重建的缓存投影。

涉及模块：

- `useStudyPersistence`
- `storage.ts`
- `study.ts`
- `backup.ts`
- `recovery.ts`
- performance diagnostics
- 数据迁移与并发 E2E

预期收益：

- 用户数据安全路径可测试、可推理。
- 小设置变化不再重写全部历史。
- 新增领域字段的修改范围明显缩小。
- 多标签页和恢复逻辑不再依赖隐式 ref 组合。

风险：

- 这是数据丢失风险最高的阶段。
- 必须提供旧 schema 读取、迁移前备份、迁移后校验和回滚验证。
- 不应同时更换 IndexedDB schema、状态管理方案和业务规则。
- 必须使用真实历史备份样本验证，不能只依靠新建测试数据。

## 8. 风险和注意事项

1. **保留现有本地数据兼容性。** `reviews`、FSRS card、undo、active session 和 quiz attempt 都可能影响排程，不能简单清空或重新生成。

2. **事件与投影要明确主次。** 建议把 `ReviewEvent` 视为事实来源，把 `WordProgress` 视为可重建投影；其他状态是否也可重建目前“不确定”，不能一概事件化。

3. **不要引入微服务。** 当前业务、部署规模和本地优先特性更适合模块化单体。拆服务会增加网络、数据一致性和部署成本。

4. **不要以文件行数作为唯一拆分依据。** 应按业务变化原因拆分。例如薄弱判断与趋势报表需要分开，是因为规则、消费者和变化频率不同。

5. **先确认指标语义。** 冲刺、复发、达标、猜错恢复和测验排程存在不确定口径。重构只能搬运已确认规则，不能借机自行定义业务。

6. **保持本地自然日一致。** 所有日期窗口应通过统一 Clock/Calendar 服务计算，并覆盖跨午夜、时区和夏令时测试。

7. **generated 文件不应手工维护。** `build-info.generated.ts` 和数据版本文件应明确生成入口，避免普通验证污染工作树。

8. **测试迁移应分层进行。** 保留关键 E2E，同时增加用例级测试；逐步删除读取源码和匹配函数名的结构测试。

9. **正式重构前重新建立基线。** 审查期间存在其他流程并行修改工作区，不能直接以本报告中的状态作为稳定起点。

总体结论：项目已有可靠的领域算法、本地数据保护和测试基础，当前主要技术债不是“功能目录不够多”，而是应用编排、持久化、分析投影和 UI 之间缺乏明确边界。最合适的演进方向是保留模块化单体，通过结构化业务契约、应用用例、仓储端口和 feature-first 目录渐进收敛，而不是整体重写。
