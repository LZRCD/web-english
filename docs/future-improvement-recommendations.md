## 一、总体判断

当前版本的主要功能、异常恢复、自动测试和生产基线已经完整。Windows 生产验证、高延迟查词预取和下一词有界音频预载均已落地；下一阶段重点转为专项性能验收、长期数据和真人设备证据。

本轮优先项：

1. Windows 生产冒烟 CI。
2. 高延迟首次查词优化。
3. 分网络条件保存和比较性能基线。
4. 慢速网络下的音频预加载。

## 二、P0：发布可靠性

### 1. 增加 Windows 生产冒烟 CI

> 状态：已完成。新增 Windows 工作流与生产冒烟脚本，本地复核后端口和 PID 均已清理。

#### 当前依据

本轮实际发现 vinext 0.0.50 在 Windows 生产环境中存在静态路径分隔符问题，导致 `/assets/*` 和 `/data/*` 返回 404。Ubuntu CI 无法覆盖这类平台差异。

#### 建议方案

- 增加 `windows-latest` CI 任务。
- 运行生产构建并在固定端口 3000 启动服务。
- 验证首页、主要 JavaScript、红宝书数据和音频索引返回 200。
- 对词典分片发出真实 `Range` 请求，验证返回 206、`Content-Range` 和响应长度。
- 健康检查结束后只关闭记录的服务 PID。

#### 验收标准

- Windows CI 能稳定启动和关闭生产服务。
- 首页完成客户端激活，红宝书 6550 词可加载。
- 静态资源无 404。
- 真实 Range 请求返回合法 206。

## 三、P1：用户可感知性能

### 1. 优化高延迟下首次查词

> 状态：已完成实现并通过方向性复核；正式验收仍需 30–50 轮同条件样本。

#### 当前数据

| 条件 | 首次查词 P50 |
|---|---:|
| 正常网络（混合异常场景） | 78.7ms |
| 原生 206 | 12.8ms |
| 250ms 高延迟 | 343.7ms |
| 受控慢速网络 | 265.9ms |
| 缓存预热 | 79.3ms |

第二轮优化后，250ms 高延迟 5 轮小样本的首次查词 P50 为 `81.7ms`、P95 为 `286.7ms`。P50 相对旧值约降低 76%，超过 20% 的方向性目标；由于只有 5 轮，暂不替代正式里程碑基线。

高延迟环境下，字母索引和词典片段的串行请求会放大网络往返成本。

#### 建议方案

- 页面进入空闲状态后，后台预取当前页面英文内容可能涉及的字母索引。
- 监听 `saveData` 和有效网络类型；省流量、2G 或离线状态不预取。
- 限制并发数和总字节数，不在首屏关键阶段争抢带宽。
- 保留当前整分片回退和内容哈希校验。

#### 验收标准

- 250ms 高延迟下首次查词 P50 降低至少 20%。
- 正常冷启动 P95 不增加超过 20ms。
- 额外后台传输量有明确上限。
- 断网、损坏片段和 200 回退测试继续通过。

### 2. 优化慢速网络下音频首播

> 状态：实现与浏览器回归已完成；慢速网络下 25% 的收益目标仍待 30–50 轮专项基线确认。

#### 当前数据

| 条件 | 原声音频首播 P50 |
|---|---:|
| 正常网络 | 16.1ms |
| 高延迟 | 121.8ms |
| 受控慢速网络 | 237.0ms |
| 缓存命中 | 9.8ms |

#### 建议方案

- 当前词使用主音频元素，页面空闲后只用第二个元素预载下一学习词。
- 下一词变为当前词时直接提升已预载元素，不覆盖正在播放的音频源。
- 省流量、2G、离线或后台标签页停止预加载；条件恢复后重新调度。
- 固定最多两个有效媒体元素，并在设置页显示占用和下一词就绪状态。
- 继续使用浏览器原生媒体片段、HTTP/Range 和解码缓存，不额外持久化整单元 MP3。

#### 验收标准

- 慢速网络下下一词音频首播 P50 降低至少 25%。
- 不增加首次页面可交互耗时。
- 缓存和网络流量上限可在诊断页查看。

### 3. 增加主动输出测验与每周报告

> 状态：已完成。专项测验与周报直接复用 FSRS、红宝书原声、错词、顽固词和考研计划。

#### 实施结果

- 听音拼写和中译英要求完整输入英文；答案归一化兼容大小写、空格、连字符和 Unicode。
- 熟词僻义优先抽取未标记熟练的后置义项；近义辨析按词性和中文释义重合度选择干扰词。
- 题目优先级由当前薄弱状态、遗忘次数和最近低评分共同决定，每组最多 10 题。
- 正确答案记为 FSRS `Good`；错误答案记为 `Again` 并立即进入薄弱词和错词队列。
- 周报按本地自然周比较掌握、遗忘与顽固词变化，预测下一周复习总量、日均与峰值。
- 已设置考研日期时，周报比较当前每日新词目标和最低所需目标，明确提示保持或调整。

## 四、P1：性能测量质量

### 1. 按相同网络条件进行跨版本比较

> 状态：已完成。网络、schema、数据版本、服务模式和主要设备环境不兼容时不生成变化或告警。

#### 当前问题

高延迟和慢速网络报告目前会与正常网络基线比较，因此会产生大量符合预期但不可操作的告警。

#### 建议方案

分别维护以下历史基线：

- `normal`
- `high-latency`
- `slow-network`
- `cache-hit`

每份新报告只与相同网络条件、诊断 schema 和主要设备环境的上一版本比较。

#### 验收标准

- 高延迟报告不再因网络条件本身触发回归告警。
- 报告明确显示对照构建、数据版本和网络条件。
- 找不到兼容基线时显示“无可比基线”，不输出误导性结论。

### 2. 明确记录运行模式

> 状态：已完成。运行模式由构建脚本生成，生产基线发现不一致时会记录错误并返回失败状态。

#### 当前问题

报告的运行标签已经记录 `serverMode=production`，但部分浏览器样本中的 `runtimeMode` 仍为 `unknown`。

#### 建议方案

- 构建时生成明确的运行模式常量。
- 样本同时记录构建模式和外部基线运行器模式。
- 两者不一致时在报告中标记错误。

#### 验收标准

- 生产报告中的样本全部标记为 `production`。
- 开发服务样本不会混入生产基线。

## 五、P2：长期维护

### 1. 控制性能报告造成的 Git 膨胀

#### 当前问题

完整 trace 报告体积较大，固定报告和 latest 报告还会重复保存。长期反复提交会永久增加 Git 历史体积。

#### 建议方案

- Git 只提交关键摘要、告警结论和正式里程碑基线。
- 完整原始 trace 保存为 CI Artifact 或独立归档。
- latest 报告由脚本或 CI 生成，不重复提交相同内容。
- 制定保留策略，例如只保留最近三个正式版本的原始报告。

### 2. 增加确定性大体量数据压力测试

#### 建议方案

- 生成接近 6550 词、数万条评分记录的固定测试夹具。
- 测量启动、旧版本迁移、备份、恢复和清理耗时。
- 校验操作前后的记录总数、revision 和抽样词卡内容。
- 压力测试不能代替真实数月数据的最终验收。

### 3. 完成真人体验验收

使用真实手机、VoiceOver、TalkBack、NVDA 或 Windows 讲述人检查：

- 触屏划词与弹窗关闭。
- 横竖屏旋转后的布局。
- 学习卡、设置页和完成摘要的朗读顺序。
- 原声音频与 TTS 回退是否真正可听见。
- 数月真实学习备份的迁移和恢复。

执行模板见 [人工体验与长期数据验收单](./manual-experience-validation.md)。

## 七、不建议立即进行的改造

- 不继续细拆词典文件，除非新的生产数据证明有必要。
- 不引入线上遥测或用户行为追踪。
- 不对所有例句执行同步二次模型审查。
- 不为了理论上的纯音频解码耗时重写整个播放体系。
- 不在没有真实失败模式前增加更多复杂降级分支。
