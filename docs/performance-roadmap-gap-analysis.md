# 词环性能、数据升级与异常恢复路线图核对

> 核对日期：2026-08-01
> 核对范围：本地性能诊断、性能基线、数据版本、Range 读取、音频、音标、存储恢复、接口边界及后续质量建设

## 一、总体结论

当前状态可以概括为：

- 功能采集框架已经完成。
- P0 工程能力大部分完成。
- P0 真实数据闭环尚未完成。
- P1、P2 多数仍处于部分完成或未开始状态。
- 当前诊断数据还不足以支持“是否拆分 Range 索引”的决定。

综合评估：P0 约完成三分之二，整个路线图约完成三分之一。

当前不应立即拆分 335KB 的 Range 索引。最重要的下一步不是继续增加埋点数量，而是让现有测量做到低干扰、可关联、可复现，并实际跑出第一份可信基线。

## 三、性能测量必须补齐的问题

### 3.1 尚无首份真实基线

目前只能手工保存基线，没有自动连续执行，也没有生成首份标准结果。

预期应增加 `perf:baseline`：

- 新浏览器上下文测试冷启动。
- 同一上下文重复加载测试热启动。
- 首次查询和重复查询成对执行。
- 分别模拟 `206`、`200`、损坏片段、网络中断。
- 导出统一 JSON。
- 记录浏览器版本、构建版本、数据版本和机器环境。

20 次只能作为最低样本量。P95 在 20 个样本时接近极端值，正式基线更适合运行 30–50 次。

### 3.2 各阶段缺少关联 ID

当前每个指标是独立样本，没有统一的 `traceId` 或 `runId`，因此无法准确回答：

> 同一次首次查词中，Range 索引占总耗时多少？

现在只能比较两个独立指标的 P50/P95，不能计算原方案要求的“Range 索引占首查耗时超过 20%”。

建议给每次启动、查词和音频播放生成统一追踪 ID：

```text
lookup trace
├─ range-index
├─ range-request
├─ json-parse
└─ result-render
```

只有同一 trace 下的阶段数据，才适合计算耗时占比。

### 3.3 诊断写入会扰动性能

当前每个阶段结束时都会同步：

1. 读取 localStorage。
2. 序列化全部样本。
3. 写回 localStorage。
4. 派发 UI 更新事件。

这会阻塞主线程，并推迟后续解析和渲染，产生观察者效应。

建议调整为：

- 先写入内存队列。
- 使用 `requestIdleCallback` 或批量定时写回。
- 页面隐藏、卸载或达到批量阈值时落盘。
- 性能计时期间不做完整 localStorage 序列化。

### 3.4 冷启动定义不够严格

当前冷／热启动主要依据 sessionStorage 标记：

- 新标签页会判定为冷启动，即使 HTTP 缓存已经是热的。
- 同标签页刷新会判定为热启动，即使资源缓存已被清理。

建议拆成两个独立维度：

- 应用启动：首次标签页／重载。
- 资源缓存：网络下载／内存缓存／磁盘缓存／304。

自动 benchmark 应使用“新浏览器 context + 清缓存”定义真正冷启动。

### 3.5 基线缺少代码构建版本

样本目前主要记录数据版本，没有记录应用代码版本。如果代码升级但数据不变，新旧代码样本会混在同一个版本下。

应增加：

- Git commit 或构建 ID。
- 诊断指标 schema 版本。
- dev／production 模式。
- 浏览器版本。
- 可选的 CPU、内存和网络环境。

### 3.6 告警没有按变体独立比较

界面可以分别展示冷／热、首次／重复、原声／TTS，但基线和回归告警主要按总体 metric 比较。

这可能掩盖：

- 冷启动变慢，但热启动变快。
- 首次查询变慢，但大量重复查询拉低总体 P95。
- TTS 变慢，被原声音频样本稀释。

基线应按“指标 + 变体标签”分别保存和比较。

## 四、Range 链路核对

### 4.1 已完成

- `206` 片段解析。
- 服务器返回 `200` 时采用整分片。
- 网络异常后整分片回退。
- 损坏片段后整分片回退。
- 对应单元测试。

### 4.2 仍需完成

#### 浏览器 E2E

现有 Range E2E 要求响应 URL 以 `.json` 结尾，但版本 URL 已带有 `?v=哈希`，原匹配规则不再适用。

#### `Content-Range` 校验

当前主要检查状态码 `206`，尚未严格验证：

- `Content-Range` 是否存在。
- 返回起止字节是否符合请求。
- 返回长度是否与范围一致。

如果代理返回错误但仍可解析的片段，可能静默查不到词，而不会触发整分片回退。

#### 请求超时

Range 索引、Range 片段和整分片回退没有独立超时。旧请求虽然不会覆盖新弹窗，但网络请求本身可能持续挂起。

#### 索引与分片一致性

Range 偏移量严格依赖对应分片字节。当前清单分别记录文件哈希，但 `ranges.json` 没有记录它由哪组分片哈希生成。

建议 Range 索引增加：

```json
{
  "version": 2,
  "prefixLength": 3,
  "shardHashes": {
    "a": "...",
    "b": "..."
  }
}
```

构建时验证所有范围；运行时发现索引与分片版本不一致时，直接回退整分片。

#### 原子升级

查询参数哈希可以让新代码绕过旧浏览器缓存，但服务器仍使用相同文件名。滚动升级时，旧页面可能用旧 Range 索引读取已经更新的新分片。

彻底解决需要内容寻址文件名或版本目录，而不仅是：

```text
i.json?v=hash
```

## 五、音频测量核对

当前已经记录：

- 索引加载与解析。
- 预加载到 `loadeddata`。
- seek。
- `audio.play()` 调用。
- `playing` 事件。
- Resource Timing 传输字节。
- TTS 回退原因。

仍存在以下问题：

- `preload.ready` 把下载、解复用和解码合并在一起。
- Resource Timing 在开始播放时可能还没有完整数据，传输字节可能为空。
- 浏览器自动播放禁用没有独立分类。
- TTS 两秒未触发 `onstart` 时会记录 `startEvent=false`，但不应当视为真正开始发声。

暂不建议为了测纯解码时间立即改成 Web Audio。可以先增加以下事件边界：

- `loadedmetadata`
- `loadeddata`
- `canplay`
- `playing`

这些阶段已经足够定位大多数音频首播问题。

## 六、数据版本与可复现构建

当前内容哈希解决了浏览器读取旧缓存的问题，但可复现构建仍未完整实现。

仍缺：

- ECDICT 上游 commit、tag 或 CSV SHA-256。
- 红宝书源文件哈希。
- 音频源文件哈希。
- FFmpeg 版本。
- Whisper 模型名称和模型文件哈希。
- 音标覆盖率与 override 数量。
- Range 最大和平均片段大小。
- 统一机器可读构建报告。

部分生成数据含实时 `generatedAt`，相同输入在不同时间重建也会得到不同哈希。

建议：

- 内容文件不写当前时间；或
- 支持 `SOURCE_DATE_EPOCH`；
- 时间信息只放入不参与内容版本计算的构建报告。

## 七、接口与密钥边界

### 7.1 已有能力

- 密钥仅从服务端环境读取。
- 查询文字有限长。
- 有上游请求超时。
- 有返回结构归一化。
- 不采用模型生成的音标作为可信音标。

### 7.2 仍需处理

- 在读取 JSON 前限制 `Content-Length`，避免先解析巨大请求再截断。
- 为 enrich 的 `word/meaning` 和 coach 的单词字段增加统一长度限制。
- 为 lookup 返回的 `meaning/note/query` 增加服务端输出长度限制。
- 增加限流和并发限制。
- 根据部署方式增加来源校验或本地访问约束。

如果应用始终只运行在 `127.0.0.1`，限流优先级较低；如果可能公开部署，API 可能成为消耗 DeepSeek 密钥的开放代理，应将限流提升为 P0。

## 九、暂时不建议做的事项

原方案中的以下限制仍然合理：

- 不对所有例句同步执行第二次模型审查。
- 不提前把词典拆成大量细碎文件。
- 不引入线上行为分析或云端遥测。
- 不因为理论上的几百 KB 增加复杂缓存层。
- 不在没有真实数据前改造 Range 索引结构。
- 不为了获得理论上的纯解码耗时立即改写整个音频播放体系。

## 十、推荐执行顺序

1. 修复并运行全部 Playwright E2E。
2. 增加 Range 超时、`Content-Range` 校验及真实降级 E2E。
3. 给性能 span 增加 `traceId`、代码构建版本和环境标签。
4. 把诊断持久化改成内存批处理，降低测量干扰。
5. 增加 30–50 轮自动 benchmark，生成第一份基线。
6. 根据同一 trace 的阶段占比决定是否拆 Range 索引。
7. 补查词竞态和存储压力测试。
8. 完善可复现数据构建报告。
9. 完善音标质量、撤销设置入口和例句反馈。
10. 最后根据真实失败案例决定是否增加轻量语义审查。

## 十一、最终判断

当前不应拆分 Range 索引。

本轮已经解决了“能不能采集”的问题，但还没有完全解决以下问题：

- 数据是否低干扰。
- 各阶段能否按同一次操作关联。
- 冷启动定义是否严格。
- 基线能否跨代码版本可靠比较。
- 浏览器级异常路径是否真的能够恢复。

只有完成自动基线、追踪关联、低干扰持久化和浏览器 E2E 后，才适合用真实数据决定后续结构优化。

## 十二、本轮执行结果（2026-08-01）

### 已完成实现

- Range：修复带版本 URL 的 E2E 匹配；严格校验 `Content-Range`、起止字节、总长度和响应长度；片段与整分片分别设置超时；补 `206`、`200`、损坏、网络中断测试；损坏用例真实进入 JSON 解析失败分支；索引最终升级为 v4，5KB 根映射随构建清单内嵌，运行时按首字母懒加载 26 个索引，并为分片与字母索引生成、保留内容寻址文件。

- 音频：新增 `loadedmetadata`、`loadeddata`、`canplay`、`playing` 阶段；记录传输与缓存信息；自动播放阻止单独分类；播放 12 秒、预加载 15 秒和 TTS 2 秒均有失败收口，播放超时自动回退 TTS。

- API 边界：三条 AI 接口在 JSON 解析前流式限制正文大小，统一输入/输出字段上限，并增加同源校验、每客户端限流、全局并发限制和可选本机访问约束。
